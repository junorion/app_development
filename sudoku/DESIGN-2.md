# 2군 설계 — 수익화와 온라인

1군을 끝낸 뒤 무엇을 어떤 순서로 할지, 그리고 **사람이 직접 해야 하는 준비**가 무엇인지
적어 둔다. 코드는 아직 쓰지 않는다 ([[BACKLOG.md]] 2군 항목의 설계 문서).

2군은 하나가 아니라 **두 덩어리**다. 준비물과 위험이 서로 다르므로 따로 다룬다.

| | **2군-A 수익화** | **2군-B 온라인** |
|---|---|---|
| 항목 | 2-4 광고 · 2-5 자동 메모 판매 · 2-6 광고 제거 · 2-7 멤버십 | 2-1 점수 연동 · 2-2 주간 등수 · 2-3 대결 |
| 서버 | **필요 없음** | 필요 |
| 인터넷 권한 | 광고 때문에 필요 | 필요 |
| 밖에서 준비할 것 | AdMob 계정, Play 판매자 프로필, 인앱 상품 | 서버/BaaS 계정, 결제 수단 |
| 운영 비용 | 없음 (Play 수수료 15%) | 서버 비용 + 개인정보 보관 책임 |
| 되돌리기 | 어렵다 (서류·문구) | 아주 어렵다 (사용자 데이터가 쌓인다) |

**권장 순서**: 1군 출시 → 2군-A → 2군-B. A 는 서버 없이 끝나고, B 는 앱의 성격을
완전히 바꾼다. 둘을 한 번에 하면 무엇이 문제인지 가려내기 어려워진다.

---

## 0. 먼저 정해야 할 것 (사람이 결정)

코드보다 앞선다. 이게 정해지지 않으면 아래 설계가 흔들린다.

| # | 결정 | 선택지 | 권장 |
|---|---|---|---|
| D1 | **2-6 "초기 5번"의 뜻** | ① 광고 5회 면제권 ② 5일간 광고 없음 | ①. 세는 기준이 분명하고, 날짜 기반은 시계를 돌리는 우회가 쉽다 |
| D2 | **자동 메모를 정말 팔 것인가** | ① 코인 소모 ② 멤버십 전용 ③ 그냥 무료 | ③ 또는 ①. 지금 무료로 쓰던 기능을 잠그면 기존 사용자에게 빼앗는 것으로 보인다 |
| D3 | **대결 규칙** | 같은 문제 동시 풀이 · 먼저 끝내기 / 제한시간 안에 많이 채우기 | 아래 2군-B 3.3 참고 |
| D4 | **계정 방식** | ① 익명 ID ② 구글 로그인 ③ 익명 시작 + 나중에 연결 | ③. 진입 장벽 없이 시작하고, 기기를 바꿀 사람만 연결한다 |
| D5 | **광고 수위** | 배너만 / 배너 + 전면 / 배너 + 보상형 | 배너 + 보상형. 전면 광고는 이탈이 크고 퍼즐 흐름을 끊는다 |

## 1. 공통 — 인터넷 권한을 켜는 순간 바뀌는 것

2군-A 든 B 든 **첫 발을 떼면 아래가 전부 다시 쓰인다.** 이건 코드보다 서류 일이 많다.

### 1.1 앱

- `AndroidManifest.xml` 에 `INTERNET` 추가
- 광고를 붙이면 `com.google.android.gms.permission.AD_ID` 도 추가된다
- **오프라인 동작을 지켜야 한다** — 비행기 모드에서 퍼즐 생성·풀이·기록은 지금처럼
  되어야 하고, 광고와 등수만 조용히 빠져야 한다. 네트워크 실패가 게임을 막으면 안 된다
- APK 크기: AdMob SDK 만 해도 몇 MB 늘어난다 (지금 290KB)

### 1.2 스토어 서류

| 문서 | 지금 | 2군에서 |
|---|---|---|
| `privacy.html` | "수집하지 않음" | 광고 ID·기기 정보·(B 라면) 사용자 ID 와 점수. 광고 파트너와 제3자 제공을 명시 |
| 데이터 보안 양식 | 수집 안 함 | 항목별 신고. 광고 ID는 "앱 활동/기기 ID" 로 잡힌다 |
| 콘텐츠 등급 | 상호작용 없음 | B 의 대결이 생기면 **사용자 간 상호작용 = 예**. 등급이 올라갈 수 있다 |
| 타깃 연령 | 13세 이상 | 그대로 두되, 광고가 붙으면 아동 대상이 아님을 분명히 해야 한다 |
| 등록정보 문구 | "광고 없음 · 인터넷 권한 자체가 없음" | **이 문장들을 지워야 한다.** 스크린샷 설명도 함께 |

> 지금 스토어 문구의 세일즈 포인트가 "인터넷 권한이 아예 없다" 이다. 이걸 버리는 것이
> 2군의 진짜 비용이다. 기능이 아니라 **약속을 되돌리는 일**이라 되돌리기 어렵다.

## 2. 2군-A · 수익화 (서버 없음)

### 2.1 밖에서 준비할 것

| # | 준비물 | 누가 | 비고 |
|---|---|---|---|
| A1 | **Play 개발자 계정 유형 확정** | 사람 | 개인이면 테스터 12명×14일. 조직이면 D-U-N-S 번호 |
| A2 | **Play 판매자 프로필**(Payments profile) | 사람 | 결제를 받으려면 신원·세금 정보가 필요하다. 승인에 며칠 걸릴 수 있다 |
| A3 | **AdMob 계정** → 앱 등록 → 광고 단위 ID | 사람 | 배너 1개, (D5 에 따라) 보상형 1개. 테스트 ID 로 먼저 붙이고 마지막에 실 ID 로 바꾼다 |
| A4 | **인앱 상품 등록** | 사람 | 정기결제 3종 — 1주 1,000원 / 2주 1,500원 / 1달 3,000원 |
| A5 | app-ads.txt | 사람 | 개발자 웹사이트가 있으면 권장. Pages 로 서빙 중이니 붙일 수 있다 |

**A2 는 시간이 걸린다.** 광고보다 결제가 먼저 막히므로 제일 먼저 신청해 두는 게 좋다.

### 2.2 광고 (2-4)

- 자리는 이미 잡혀 있다 — `#adSlot`, 게임 화면 맨 아래 50px. 지금은 빈 여백이고
  보드 크기 계산에도 이미 반영돼 있어서 광고가 들어와도 배치가 흔들리지 않는다
- 배너는 **게임 화면에만**. 홈·설정·완료 화면에는 넣지 않는다
- 보상형 광고(D5)를 넣는다면 자연스러운 자리는 **코인이 0일 때 힌트를 누른 순간**이다.
  지금 그 자리에 "코인이 모자랍니다" 안내가 이미 있다 — 거기에 "광고 보고 코인 1개"
  버튼을 더하면 된다
- **전면 광고는 권하지 않는다.** 새 게임마다 끼면 이탈이 크고, 지금 앱의 조용한 성격과
  맞지 않는다

### 2.3 코인과 멤버십 (2-5·2-6·2-7)

지금 코인 경제는 이렇다 — 시작 10개, 힌트 1개 소모, 한 판 끝내면 1개 획득.
여기에 살을 붙인다.

| 얻는 길 | 지금 | 2군-A |
|---|---|---|
| 시작 지급 | 10 | 그대로 |
| 판 완료 | +1 | 그대로 |
| 보상형 광고 | — | +1 (하루 상한 필요, 예: 5회) |
| 멤버십 | — | 힌트 무제한 또는 매일 지급 |

멤버십이 주는 것(안): **광고 제거 + 힌트 무제한 + 자동 메모**. 셋을 묶어야 값이 선다.

**구현에서 조심할 것**

- 결제 상태는 **Play 라이브러리에 물어서** 정한다. 로컬에 "멤버십 = true" 만 저장하면
  기기 시간을 돌리거나 저장소를 만지는 것으로 뚫린다
- 서버가 없으므로 **영수증 검증이 완전하지 않다.** 초기에는 감수하고, B 로 서버가
  생기면 그때 서버 검증을 붙인다
- 구매 복원 경로가 반드시 있어야 한다 (기기 변경·재설치)
- 환불·구독 취소 시 즉시 반영

### 2.4 순서

1. 인터넷 권한 + AdMob SDK, **테스트 광고 ID** 로 배너만 띄운다
2. 오프라인에서 광고만 빠지고 게임은 그대로인지 확인
3. 결제 라이브러리 연결, 멤버십 상품 하나로 먼저 (1달)
4. 광고 제거 · 힌트 무제한 · 자동 메모를 멤버십에 연결
5. 보상형 광고
6. 서류 다시 쓰기 → 실 광고 ID 로 교체 → 업로드

## 3. 2군-B · 온라인 (서버 필요)

### 3.1 서버 선택지

| 방식 | 장점 | 단점 |
|---|---|---|
| **Firebase** (Firestore + Auth + Functions) | 계정·DB·서버 코드가 한 벌. 초기 무료 티어로 충분 | 요금이 사용량에 붙어 예측이 어렵다. 대결의 실시간성은 Realtime DB 가 낫다 |
| 직접 만든 서버 (VPS) | 비용 예측 가능, 통제권 | 운영·보안·백업이 전부 내 몫 |
| Supabase 등 | Postgres 라 등수 쿼리가 편하다 | 실시간 매칭은 따로 설계해야 |

**권장**: Firebase. 등수(Firestore) + 대결(Realtime DB) + 검증(Functions) 을 한 곳에서
할 수 있고, 앱이 작아 무료 티어를 넘길 일이 당분간 없다.

### 3.2 주간 등수 (2-2) — 여기서 가장 어려운 것은 부정 점수

클라이언트가 보낸 점수를 그대로 믿으면 안 된다. 저장소를 고치거나 통신을 흉내내면
아무 점수나 올릴 수 있다. 막는 방법을 강한 순서로 적는다.

1. **서버가 문제를 낸다** — 데일리처럼 날짜 씨앗으로 만든 문제만 등수에 넣는다.
   서버가 정답을 알고 있으므로 "그 문제를 그 시간에 풀었다" 를 검증할 수 있다
2. **풀이 과정을 함께 보낸다** — 수순과 시각을 보내고 서버가 재생해 본다. 사람이 낼 수
   없는 속도(예: 3초에 30수)는 거른다
3. 같은 계정의 비정상 패턴(하루 100판, 늘 최고 기록)을 표시해 둔다

**가장 현실적인 시작점**: 등수 대상을 **데일리 퍼즐 하나로 한정**한다. 문제가 하나뿐이라
서버가 정답과 최소 풀이 시간을 알고 있고, 비교도 공정하다. 자유 게임까지 등수에 넣으면
문제마다 난이도가 달라 애초에 비교가 성립하지 않는다.

### 3.3 대결 (2-3) — 규칙부터 (D3)

| 방식 | 내용 | 평가 |
|---|---|---|
| **동시 풀이 · 먼저 끝내기** | 같은 문제를 같이 시작해 먼저 완성한 쪽이 이긴다 | 규칙이 단순하고 스도쿠와 잘 맞는다. 실력 차가 크면 한쪽이 지루하다 |
| 제한시간 안에 많이 채우기 | 5분 동안 더 많은 칸을 맞춘 쪽이 이긴다 | 이탈이 적고 판이 짧다. 실수 처리 규칙이 필요하다 |
| 비동기 대결 | 같은 문제를 각자 아무 때나 풀고 기록을 비교 | 서버가 훨씬 단순하다(실시간 연결 불필요). 대결하는 맛은 덜하다 |

**권장**: **비동기 대결로 시작**한다. 실시간 매칭·접속 관리·중도 이탈 처리는 2군에서
가장 비싼 부분인데, 비동기면 그게 전부 사라진다. 반응이 좋으면 그때 실시간을 얹는다.

정해야 할 세부: 시간 제한, 힌트 사용 허용 여부(허용하면 코인 있는 쪽이 유리하다),
중도 이탈 처리, 실력 기반 매칭 여부.

### 3.4 계정 (D4)

익명 ID 로 시작하고, 원하는 사람만 구글 계정에 연결한다. 익명만 쓰면 앱을 지우는 순간
등수와 기록이 사라진다는 것을 화면에 알려야 한다.

**개인정보**: 익명 ID + 점수 + 완료 시각만 다뤄도 개인정보 처리자가 된다. 삭제 요청
경로(설정 안 "계정과 기록 삭제")를 반드시 만든다 — Play 정책 요건이기도 하다.

## 5. 이 문서를 고칠 때

결정(D1~D5)이 내려지면 그 줄에 결과와 날짜를 적는다. 설계가 바뀌면 백로그의 2군 메모도
같이 고친다 — 두 곳이 어긋나면 나중에 어느 쪽이 맞는지 알 수 없다.
